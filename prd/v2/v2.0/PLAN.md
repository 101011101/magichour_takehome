# v2.0 Plan — the two-bucket architecture and the harness that tested it

> **Reconstructed 2026-08-15, after the runs.** See [README.md](README.md). The
> architecture below is what was built; this document describes it rather than
> having specified it in advance.

## 1. The structural decision: two buckets, not one model

The shipped product is a **pipeline, not a single model**. That was settled
before any arm was run, and it shapes everything else.

| Bucket | Shape | Selected on | Why it is separate |
|---|---|---|---|
| **Editing** | person + garment in, try-on out | **fidelity** (garment ×2, identity, scene) | Multi-image input, so it carries the attention failure modes: identity drift, garment leakage, background repaint |
| **Auxiliary realism** | one image in, same image out but more realistic | **realism gain, gated on fidelity preservation** | Single-image input means it is *structurally* free of multi-image attention failures |

The argument for the split: the editing bucket's weak axis is realism —
artifacts, hands, plastic skin — and repairing that *at the editing stage* risks
the fidelity the editing stage exists to deliver. Moving realism to a stage that
cannot see a second image removes the failure mode by construction rather than
by prompt.

This is the same reasoning that later produced v2.2's cropping: **prefer a
structural fix over arguing the model out of a behaviour.**

## 2. Consequence for how the comparison had to be run

Because the product is a pipeline, the editing arms could not be ranked in
isolation. Two arms can trade fidelity against realism, and the realism half is
repairable downstream while the fidelity half is not. The plan was therefore:

1. Screen editing arms on fidelity, eliminating on deterministic metrics.
2. Screen auxiliary configs **against their own input** — a different question
   from the editing screen, asking "did it change what it was given?" rather than
   "did it perform the edit?".
3. Decide the base on the axis that survives the second stage: **garment
   transfer**, since the auxiliary stage repairs realism but cannot restore a
   garment the editor failed to transfer.

Point 3 is the whole reason the FASHN-vs-klein contest resolved the way it did.

## 3. Scoring architecture

Three layers with explicitly different authority
([CONDITIONS.md §4](../results_summary/CONDITIONS.md),
[SCORING_CRITERIA.md](../SCORING_CRITERIA.md)):

| Layer | Mechanism | Authority |
|---|---|---|
| **Deterministic** (free, local CPU) | FashionSigLIP garment similarity, AuraFace identity, pose displacement, background PSNR → fixed-anchor weighted composite, garment ×2 | **Elimination** |
| **VLM judge** (blind gpt-5.5) | Six 1–5 criteria bucketed into fidelity (garment, identity, scene) and realism (clean, hands, realism), plus `wrong_person`; schema-validated with self-correcting retries | **Realism**, where deterministic metrics are weak |
| **Human review** | Side-by-side inspection | **Final tiebreaker** |

Two design details worth keeping:

- **Fixed anchors, recalibrated on V1 outputs.** The identity ceiling sits
  deliberately *below* paste-back saturation, so a compositing arm cannot max the
  score by construction. A metric that a degenerate strategy can win is not a
  metric.
- **The judge is closed-weights by design.** gpt-5.5 is an evaluation
  instrument, not part of the deployed path, so the open-weights constraint does
  not apply to it.

**Known weakness, identified later:** this architecture gives elimination
authority to deterministic metrics that v2.2 showed can miss a total
transfer failure — `garment_sim` is an embedding cosine that rewards a
*plausible* garment, so a non-transfer still scores 0.78. Nothing was eliminated
in v2.0 on a score that later proved unsafe, but the authority table was too
generous and v2.2 revised it.

## 4. Harness

| Component | Role |
|---|---|
| `v2/build/ts2_harness.py` | The editing comparison. `--generate --score --judge --html`; `CONFIGS` table defines the arms; `prompt_for()` is the single source of prompt truth (imported, never re-implemented, so a later run is a parity test rather than a different experiment) |
| `v2/build/aux_harness.py` | The auxiliary screen: generate → deterministic scoring → pairwise VLM → page |
| `v2/build/aux_batch.py` | The two-batch control design (added during v2.1) |
| `v2/build/metrics_v2.py` | Deterministic metric implementations and the composite |
| `v2/build/make_compare.py` | The V1-set triage page |
| `v2/build/make_klein_page.py` | The distilled-vs-base head-to-head page |
| `v2/build/notebook_cells.py` | Notebook cell bodies, kept in a `.py` so they are diffable |

Every page in `v2/artifacts/` is generated by exactly one script; none is
hand-edited. Run packages, metrics CSVs and images land in `v2/runs/`.

## 5. Pipeline target that came out of this

**FLUX.2 klein 4B distilled → SeedVR2 (noise 0)**, with FASHN v1.5 retained as
the documented fallback for the strict-preservation case.

A superseded klein composite (`composite_v2ow`: klein → geometric face
paste-back → Z-Image refine → AuraFace identity gate with best-of-N retry) is
kept in the harness as a reference implementation of the paste-back and gate
machinery — the retry/reseed half of it is reused for klein's failure handling
in [v2.2.3](../v2.2/).
